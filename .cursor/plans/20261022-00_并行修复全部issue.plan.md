## 风险与回滚

- **并行冲突**：4 个 worker 文件所有权隔离；README/main.py/共享文件由主 agent 串行集成。冲突时以 issue 验收为准手工合并，禁止丢弃任一 worker 的已完成修复。
- **大重构回归**：main.py 拆分、app.js 模块化、SQLite 迁移均可能引入回归；每个 worker 必须小步提交并跑对应测试；合并后跑全量测试与 E2E，失败则回滚该 merge commit（保留分支）。
- **SQLite UEs**：任何停服/重启前先 checkpoint；worktree 内测试使用独立数据目录，禁止并发写主 checkout 的 `data/`。
- **Docker 非 root 卷权限**：现有命名卷可能 root 所有；entrypoint 以 root 修权限后降权，若不可行则保持 USER 非 root 并在 README 说明新卷要求；部署验证失败只回滚 Dockerfile/entrypoint，不影响代码。
- **Issue 语义变化**：长任务改 202 是 breaking change，必须同步前端与回归测试；若上游调用方无法一次改完，保留同步 `?sync=true` 兼容入口并记录。
- **监控自动化**：只创建只读检查 + 修复的定时任务；若用户不确认则仅在本会话内轮询，不创建后台自动化。

## 关键决策记录

1. **4 个 worker 而非严格 3 个**：P2 有 9 个 issue，且 `main.py` 同时承载 #11/#14/#15/#18；按文件所有权切为 P2a/P2b，避免单会话轮次耗尽与相互覆盖，仍按 P1/P2/P3 优先级管理。
2. **前端统一归 P1**：#8 与 #12 都修改 `app.js`，由同一 worker 先做安全渲染再做模块拆分，避免并行冲突；#15 的前端进度由 P1 按固定 jobs 契约接入。
3. **README 不在 worker 内改**：四个分支都会涉及文档，集中由主 agent 在合并后一次性更新，避免冲突。
4. **任务持久化用独立 `data/jobs.db`**：避免与 #16 的 `funnel_state.db`/`market_kline.db` 迁移改造冲突，同时满足重启后可见。
5. **不直接关闭 issue**：worker 只提交/推送分支；主 agent 合并、验证、评论并关闭，保证对外状态与真实代码一致。
