# 数据中心覆盖率显示修复 + 历史深度扩展

> 来源：2026-08-25 用户截图反馈"覆盖率仅5.7%太少了"。本文件只增不删。

## 背景 / 目标

截图显示覆盖率 5.7%/缺失 141,664 条，实测为**过期报告**（回补前生成，手动同步完成后不重检）。真实覆盖率 88.65%（近30个交易日缺 17,268 条，系上次大规模回补限流残留）。另外当前 K 线仅回溯到 2026-03-03（约半年），用户希望更深历史。

目标：
1. 修复过期报告误导：任何 sealed 同步完成后自动重检（30 天窗口），前端识别过期报告降级告警。
2. 补齐近 30 日真实缺口（后台进行中）。
3. 历史深度从 120 天扩展到最多 3 年（window clamp 365→1095），并执行一次 3 年深回补。

## 任务分解（checklist）

- [ ] 后端：sealed 成功后自动触发 `check_data_integrity(days=30)` 后台任务（服务内持引用防 GC）；`kline_cache_loop` 内联重检去重
- [ ] 后端：window_days 上限 365 → 1095（__init__ / sync_trade_date / initialize 端点三处）
- [ ] 前端：renderDcStats 识别 report.check_time < syncStatus.updated_at 时，红色告警降级为琥珀色"报告已过期，自动重检中"
- [ ] 等待缺口补缺完成 → 重建镜像 → 重启容器
- [ ] 触发 3 年深回补（window_days=1095），验证覆盖率
- [ ] README：initialize 参数范围、数据回溯深度说明
- [ ] pytest + 提交 push

## 验收标准

1. 手动同步完成后 ~1 分钟内 report 自动刷新（check_time > updated_at）
2. 过期期间 UI 不再显示红色"严重缺失"误报
3. 深回补完成后 min_date ≈ 3 年前，近 30 日覆盖率 ≥ 95%
4. 全套测试通过，推送 GitHub

## 风险与回滚

- 3 年回补请求体变大，单 symbol 仍为 1 次请求；东财 kline API beg/end 模式无 lmt 截断风险（回补后用报告验证）
- 1095 天窗口的全量同步耗时约 30-60 分钟（5000+ symbol），期间 UI 可正常使用
- 回滚 = revert 对应 commit

## 关键决策记录

1. 自动重检放服务层而非路由层：手动/初始化/自动三条路径统一覆盖。
2. 前端只做告警降级不做自动触发检查：避免多个浏览器 tab 重复触发重检查。
