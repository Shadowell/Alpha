# 打板 / 短线 Alpha 功能挖掘与 Issue 创建

## 背景 / 目标

Alpha 当前主线是 A 股选股 + Kronos 预测 + Hermes 自进化 + 模拟盘。用户要求以资深金融数据量化交易产品经理视角，挖掘所有能产生 alpha 的功能，重点聚焦**打板 / 短线策略**，并创建 P1/P2/P3 分级 issue。

核对现状后发现两个关键缺口：

1. `FirstLimit Alpha` 的 README 已列出封板质量、板块共振、情绪周期、股性、可交易性等正确方向，但 `strategy/first_limit_alpha/features.py` 实际只有约 46 个日线 OHLCV 特征；`limit_quality` 只是 K 线代理。
2. 正在推进的 Tushare 扩展计划只覆盖 `daily_basic`、`stk_limit`、`adj_factor`、`moneyflow`、`moneyflow_hsgt`、`index_daily`、`rt_min`，缺少打板最核心的 `limit_list_d`、`limit_step`、`kpl_list`、`top_list`、`top_inst`、`hm_detail`。

因此本轮以「数据底座 → 可执行标签 → 因子族 → 可成交性回测 → 分层模型」为主线，创建 15 条功能 issue。

## 验收标准

- 15 条 issue 全部存在，标题、优先级标签、正文结构完整。
- 每条正文包含：现状与故障描述、功能描述、因子 / 工作清单、数据依赖、验收标准、风险与约束、关联 issue。
- 所有因子 / 标签明确要求 Point-in-Time、防未来函数、可成交性约束与幸存者偏差处理。
- P1 六条形成闭环：数据 → 标签 → 微观结构 / 情绪因子 → 可成交性回测 → 分层模型与因子评估。
- P2 / P3 均标注依赖关系，避免与 P1 重复建设。

## 风险与回滚

- **权限风险**：`limit_list_d`、`kpl_list`、`top_list`、`hm_detail`、`stk_mins`、`stk_auction`、`cyq_perf` 等 Tushare 接口需要积分 / 权限；实施前先做能力探测，不可用则按 issue 中降级方案处理。
- **未来函数**：所有因子 / 标签 / 回测必须按可见时间对齐；盘中因子带 `as_of_time`；训练使用 walk-forward + embargo。
- **过拟合**：打板样本少、噪声大；复杂模型只在样本外有增量时保留，不达标不上线。
- **可成交性**：一字板、涨停排队、跌停/停牌不可卖必须建模；strict 口径作为默认展示。
- **回滚**：issue 为研究与实施任务，不涉及生产代码；若某方向无增量，在 issue 中记录结论并关闭，不删除历史。

## 关键决策记录

1. **聚焦打板 / 短线，不创建泛产品化 issue**：多用户、移动端、实盘券商接入等不直接产生打板 alpha，本轮不建。
2. **数据底座优先**：没有涨停板 / 封单 / 连板 / 龙虎榜数据，后续因子与模型都是 K 线代理，因此 #22 是最高优先级。
3. **标签以可执行为准**：不再用“次日开盘买入”作为唯一入场假设；同时提供 T 日涨停价排队与 T+1 竞价两种场景，并强制可成交性标签。
4. **情绪周期独立成族**：打板 alpha 强依赖 regime；#25 不仅做特征，还要输出可回测的 regime 标签，供 #27、#32 使用。
5. **模型分层**：首板、1进2、2进3、高位板、反包板分开建模，避免混合样本互相稀释。
6. **P3 保持研究性质**：另类数据、游资画像、事件驱动、深度模型必须先做增量验证，不直接进生产。
