# 部署 Alpha 到 tokyo 服务器（alpha.notenap.com）

## 背景 / 目标

- 现状：Alpha 仅有本机 Docker 配置，未部署到任何服务器；本机服务当前未运行。
- 目标服务器：`tokyo`（64.83.43.61，Ubuntu 22.04，8C/15G，磁盘剩余约 24G）。
- 目标：用 Docker Compose 部署到 `/opt/alpha`，迁移本地 K 线库（约 960MB）与漏斗库，通过 `alpha.notenap.com` 对外提供 HTTPS 页面，并保留本机私密性可控的访问边界。
- 访问方式：沿用机队现有 Nginx SNI 分流 + Let's Encrypt；新增站点回环端口 `127.0.0.1:8461`，并加 Nginx Basic Auth（Alpha 读接口本身无鉴权）。

## 关键决策

- 域名：`alpha.notenap.com`（`notenap.com` NS 为阿里云 hichina，当前无该记录）。
- DNS：通过浏览器登录阿里云 DNS 控制台新增 A 记录 → 64.83.43.61，TTL 600。
- 不设置 `ALPHA_WRITE_TOKEN`：access_guard 在配置 token 后要求所有写请求带 `X-Alpha-Token`，而网页前端不带该头，会导致页面写操作全部失败。安全边界放在 Nginx Basic Auth，容器端口仍只绑 `127.0.0.1:18888`。
- 容器保留 `ALPHA_TRUST_EDGE=1`（Docker NAT 适配）；写权限由 Basic Auth + 宿主机回环绑定共同保护。
- 数据迁移：停服 checkpoint → SQLite backup API 导出快照 → zstd 压缩传输 → 容器停止状态下写入 `alpha_data` 命名卷 → 启动校验。
- 单实例运行：uvicorn 单 worker，禁止水平扩容（进程内调度 + SQLite）。

## 验收标准

- `https://alpha.notenap.com` 经 Basic Auth 登录后页面正常，未认证返回 401。
- `/api/funnel`、`/api/kline-cache/...` 等只读接口返回正常；`/ws/realtime` 101 升级成功。
- 迁移后 `market_kline.db` 行数与本地一致，漏斗状态/策略配置可见。
- 容器 `restart: unless-stopped`、healthcheck healthy；服务器重启后自动拉起。
- 除 127.0.0.1:18888 外无新增公网端口；现有服务、证书和 SNI 路由不受影响（reload 前后逐项核对）。

## 风险与回滚

- **磁盘**：镜像约数 GB + DB 1GB + 每日备份最多 7 份（约 7GB），当前剩余 24G。部署后监控；必要时下调备份保留份数。
- **内存**：仅剩约 5.3G 可用且 swap 接近满；Kronos CPU 推理可能吃紧。若 OOM，先限制并发/停用 Kronos 预测，再评估扩容。
- **DNS/证书**：DNS 未生效会导致 certbot 失败；失败则清理 Nginx 新配置与 SNI 条目，域名不影响现有站点。
- **Nginx 影响面**：SNI map 与站点目录为共享配置；修改前备份原文件，`nginx -t` 失败立即还原；reload 为平滑操作。
- **数据**：迁移前保留本地原始库与备份；服务器端写入前确认容器已停止，禁止直接 cp WAL 活跃库。
- **回滚**：`docker compose down`（保留卷）→ 删除 Nginx 站点与 SNI 条目 → reload → 删除 DNS 记录；本地数据不动。
